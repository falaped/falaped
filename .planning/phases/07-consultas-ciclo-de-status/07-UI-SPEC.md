## Color

60/30/10 split built entirely on existing oklch tokens. The primary is the soft pediatric **blue** (`oklch(0.7603 0.0916 255.41)`) — this is the ONLY brand accent hue.

> **Reconciliation with Phase 6 "verde = disponível":** The Phase 6 code renders **available slots as `bg-primary/25`** (the blue primary) and the UI copy calls this the "disponível" state. Phase 7 keeps that exact treatment for free/available slots and layers appointment states on top **without reusing the plain `bg-primary/25` fill** for any booked state, so a free slot is never confused with a booked one.

| Role | Token | Value (light) | Usage |
|------|-------|---------------|-------|
| Dominant (60%) | `--background` | `oklch(0.985 0 0)` | Page background, empty grid area, month grid |
| Secondary (30%) | `--card` / `--secondary` / `--muted` | `oklch(1 0 0)` / `oklch(0.967…)` / `oklch(0.97 0 0)` | Dialog/card surfaces, pending-requests panel, gutter, day headers, **folga cells (`bg-muted`)** |
| Accent (10%) | `--primary` | `oklch(0.7603 0.0916 255.41)` | See reserved list below |
| Destructive | `--destructive` | `oklch(0.58 0.22 27)` | Reject-request / cancel confirmation actions only |

**Accent (primary blue) reserved for — explicit, closed list:**
1. **Free/available slot cells** (inherited, D-06 Phase 6): `bg-primary/25 hover:bg-primary/35` — the slot the doctor can click to create a consulta. Unchanged from Phase 6.
2. **Confirmed appointment** fill (see status table): a stronger, solid-feeling primary treatment that reads as "firmado".
3. The single primary CTA in the creation dialog ("Agendar consulta") and the "Confirmar" action on a pending request.
4. The active view tab and today marker (inherited).

**NOT accent (neutral/secondary tokens):** grid lines (`border-border`), time/day labels (`text-muted-foreground`), folga cells (`bg-muted`), secondary buttons (`variant="outline"`/`ghost`), the request-list container.

### Appointment status color system (SC-2 / SC-3 — the core new contract)

The token palette offers **one brand hue (blue), one destructive hue (red), and neutrals** — the 5 chart tokens are all blue-ramp variants and are **not** perceptually distinct, so status cannot be encoded by hue alone. Each status is therefore encoded by a **triple: fill/border treatment + a lucide icon + a `Badge` label**, guaranteeing the required distinctions even for colorblind users and inside a 24px cell.

| Status | DB value | Cell fill + border | Icon (lucide) | Badge variant + label | Must be distinct from |
|--------|----------|--------------------|---------------|-----------------------|-----------------------|
| **Disponível** (free slot — not an appointment) | — | `bg-primary/25`, no border | — | none | all booked states |
| **Pendente** (pedido a confirmar) | `pending` | `bg-primary/10` + **dashed** `border-primary/60` (border-dashed) | `Clock` (primary) | `variant="outline"` text-primary — "Pendente" | **Confirmada (SC-3): dashed+light vs solid+filled** |
| **Confirmada** | `confirmed` | `bg-primary/70 text-primary-foreground` + solid `border-primary` | `CalendarCheck` | `variant="default"` — "Confirmada" | Pendente (solid vs dashed) |
| **Realizada** | `done` | `bg-muted` + solid `border-border`, `text-muted-foreground` | `Check` | `variant="secondary"` — "Realizada" | Falta / Cancelada |
| **Falta** (no-show) | `no_show` | `bg-destructive/10` + solid `border-destructive/40`, `text-destructive` | `UserX` | `variant="destructive"` — "Falta" | **Cancelada (SC-2): filled destructive-tint + UserX vs. hatched neutral + strikethrough** |
| **Cancelada** | `canceled` | `bg-muted` + **diagonal-hatch** overlay, `text-muted-foreground` **line-through** on the name | `CalendarX` | `variant="ghost"` text-muted-foreground — "Cancelada" | **Falta (SC-2): neutral+strikethrough vs. destructive-tint** |

**Why Falta ≠ Cancelada (SC-2, explicit):** Falta uses a **destructive tint fill + `UserX` icon + destructive badge** (the patient failed to show — a negative clinical event). Cancelada uses a **neutral muted fill + diagonal hatch + strikethrough name + `CalendarX`** (the appointment was called off — no blame, released the slot). Different fill family, different icon, different badge variant, different text decoration. They can never be confused.

**Why Pendente ≠ Confirmada (SC-3, explicit):** Pendente is **low-emphasis blue with a dashed border** ("not yet firm"); Confirmada is **high-emphasis solid-filled blue with `primary-foreground` text** ("firmado"). Dashed-vs-solid border + light-vs-filled fill is legible at 24px.

**Coexistence with Phase 6 language (no clash):**
- Free/available stays `bg-primary/25` (unchanged). Booked states never use the bare `/25` fill — pendente is lighter (`/10` + dashed), confirmada is much stronger (`/70` filled). A doctor scanning the grid distinguishes "livre" (flat light blue) from "pendente" (dashed outline) from "confirmada" (solid filled).
- Folga stays neutral `bg-muted` (D-15). Realizada and Cancelada also live in the neutral family (historical/inactive) but are always paired with an icon + badge, and appear only where a folga cannot (a folga cell has no appointment), so the neutral overlap is not ambiguous in practice; the badge/icon disambiguates on hover/focus and in the detail popover.

**Semantic reservation:** destructive red is used ONLY for (a) the Falta status tint, (b) the "Recusar"/"Cancelar" confirmation action. It is never used for folga (a day off is not an error — D-15 inherited).

## Copywriting Contract

All strings PT-BR, professional and direct (audience: pediatra). Terminology per project skill (Paciente = criança; Responsável = nome completo).

| Element | Copy |
|---------|------|
| Primary CTA (creation dialog) | Agendar consulta |
| Primary CTA — saving state | Agendando... |
| Creation dialog title | Nova consulta |
| Creation dialog description | {data} · {horário} — escolha o paciente para agendar neste horário. |
| Patient search field label | Paciente |
| Patient search placeholder | Buscar por nome do paciente ou responsável… |
| Confirm a pending request | Confirmar |
| Reject a pending request | Recusar |
| Mark as done | Marcar como realizada |
| Mark as no-show | Marcar falta |
| Cancel a confirmed appointment | Cancelar consulta |
| Pending-requests panel heading | Pedidos a confirmar |
| Pending-requests count badge | {n} pendente(s) |

### Empty states (dashed-border pattern: `rounded-xl border border-dashed p-8 text-center`)

| Surface | Heading | Body + next step |
|---------|---------|------------------|
| Calendar — day/week with no appointments yet | Nenhuma consulta agendada. | Clique num horário livre (azul) para agendar uma consulta. |
| Pending-requests panel — none pending | Nenhum pedido a confirmar. | Os pedidos de agendamento aparecem aqui quando a assistente marca uma consulta. |
| Patient search inside dialog — no results | Nenhum paciente encontrado. | Verifique o nome ou cadastre o paciente antes de agendar. |
| Patient search inside dialog — before typing | Comece a digitar para buscar. | Busque um paciente já cadastrado por nome ou responsável. |

> **Note (D-04):** patient **creation** is out of scope this phase — the "cadastre o paciente" copy points the doctor to the existing patients flow; the dialog only *selects* an existing patient.

### Loading states

- Use existing `Skeleton`. Patient search results: skeleton rows inside the `Command`/`Combobox` list while `getPatientsByProfileId` resolves. Calendar with appointments loading: keep the grid frame (gutter + headers) and skeleton the slot cells — never a bare full-page spinner. Creation submit: disable the CTA and show the "Agendando..." label with an inline `Loader2` spinner (matches the Phase 6 Salvar pattern).

### Error states

| Situation | Copy (problem + path forward) |
|-----------|-------------------------------|
| **Horário já ocupado (double-booking, D-08 / 23P01 → result union)** | Este horário já foi ocupado por outra consulta. Escolha outro horário livre. |
| Create appointment failed (generic) | Não foi possível agendar a consulta. Verifique sua conexão e tente novamente. |
| Confirm/reject request failed | Não foi possível atualizar o pedido. Tente novamente. |
| Status transition failed | Não foi possível atualizar a consulta. Tente novamente. |
| Load appointments failed | Não foi possível carregar as consultas. Atualize a página para tentar novamente. |
| Slot no longer free (server revalidates D-02) | Este horário não está mais disponível. Atualize a agenda e escolha outro. |
| No patient selected (Zod validation) | Field-level, `text-destructive text-sm` below the search: "Selecione um paciente para agendar." |

The **"horário já ocupado"** case is the single most important copy: the DB exclusion constraint (23P01) is caught in the action and returned as a friendly result union — the toast/inline message MUST be the copy above, never a raw Postgres error.

Action outcomes surface via `sonner` toast (success + error), consistent with the repo and Phase 6.

### Destructive / final-state actions

| Action | Confirmation approach |
|--------|-----------------------|
| **Recusar pedido** (pending → cancelada; releases the slot) | `AlertDialog`: title "Recusar este pedido?", body "A consulta de {paciente} em {data} {horário} será cancelada e o horário liberado. Esta ação não pode ser desfeita.", confirm "Recusar" (`variant="destructive"`), cancel "Voltar". |
| **Cancelar consulta** (confirmed → cancelada; final state, releases slot) | `AlertDialog`: title "Cancelar esta consulta?", body "A consulta de {paciente} em {data} {horário} será cancelada e o horário liberado. Esta ação não pode ser desfeita.", confirm "Cancelar consulta" (`variant="destructive"`), cancel "Voltar". |
| **Marcar falta** (confirmed → no_show; final state) | Lower-friction confirm — a `dropdown-menu`/popover action item; no `AlertDialog` required, but the item text is explicit ("Marcar falta") and the result is a toast. Falta is final (D-06) but not slot-releasing-with-loss; a single tap with clear labeling is acceptable. |
| **Marcar como realizada** (confirmed → done; final state) | Non-destructive; direct action item in the status menu, toast confirmation. No AlertDialog. |

`realizada`, `falta`, `cancelada` are **final states** (D-06) — the status menu on a final-state appointment shows no further transitions (read-only detail + the historical badge).

## Key Layout & Interaction Contract (phase-specific)

> Resolves the open UI questions flagged as "Claude's discretion" in 07-CONTEXT.md (how appointments render over Phase 6 slots; where the pending-requests list lives; the creation and status-transition affordances), honoring D-01..D-11 and the Phase 6 grid.

### 1. Creation dialog (D-03 / D-04 / D-05)

- **Entry point:** clicking a **free/available cell** (`bg-primary/25`) in the Dia/Semana grid opens the **creation dialog**. This is a NEW left-click behavior that must coexist with Phase 6's existing left-click "Disponibilidade" menu.
  - **Disambiguation rule (contract):** a **free/available** cell → left-click opens **Nova consulta** (appointment creation). An **empty** cell (no availability) keeps the Phase 6 "Disponibilidade" menu behavior. Right-click (folga) is unchanged. If the editor exposes an availability-edit vs. appointment mode, the appointment path is the primary reading of a left-click on an *available* slot (the doctor's frequent action, per design skill "priorizar velocidade em ações frequentes"). The exact toggle/mode mechanics are the planner's to implement, but a click on a free slot MUST reach appointment creation without a mode-switch detour.
- **Surface:** `Dialog` (centered modal) — not the virtual popover — because it hosts a search + selection flow that needs focus and space. Reuse the anchoring lesson from `availability-cell-menu.tsx` only if a lighter popover is chosen for very small viewports; default is `Dialog`.
- **Header:** title "Nova consulta"; description shows the locked **{data} · {horário}** derived from the clicked slot (the appointment occupies exactly that 1 slot, D-01 — no duration/time editing in the dialog).
- **Body — patient search (D-04, reuse patients domain):**
  - Single field: a `Command`(cmdk)- or `Combobox`-based search that queries the existing `getPatientsByProfileId` / `findPatientByProfileIdNameAndResponsible` (scoped by `profile_id`). Client-side filter over the profile's patients is acceptable (mirrors the existing module).
  - Each result row: patient **name** (`text-base`) + **responsável** (`text-sm text-muted-foreground`) — the minimum identifying pair per the pediatric skill. Optional `avatar` on the left.
  - States: **before typing** → "Comece a digitar para buscar."; **loading** → skeleton rows; **no results** → "Nenhum paciente encontrado."; **selected** → the chosen patient shown as a confirmed selection (name + responsável) with a clear "trocar" affordance.
  - **No patient creation here** (D-04) — selection only.
- **Footer:** primary CTA "Agendar consulta" (accent, disabled until a patient is selected; "Agendando..." while saving); secondary "Cancelar" (`variant="ghost"`).
- **On success (D-05):** the appointment is created **Confirmada** (doctor-created) and appears immediately in the grid cell as the Confirmada treatment; toast "Consulta agendada." The dialog closes.
- **On double-booking (D-08):** the action returns the friendly "horário já ocupado" result union → inline error inside the dialog (not a raw error), CTA re-enabled so the doctor can close and pick another slot.

### 2. Appointment rendering on the calendar (SC-2 / SC-3)

- A booked slot **replaces** the free-slot fill in that exact grid cell with its status treatment from the color table (fill + border + icon + inline `text-xs` patient last name/first token). It occupies **one cell** (D-01).
- **Hover/focus** on a booked cell shows a `tooltip`/lightweight detail: full patient name, responsável, status badge, and (for non-final states) the status-transition menu trigger.
- **Historical appointments stay visible (D-07):** realizada / falta / cancelada remain rendered in their neutral/destructive-tint treatment even though the underlying slot is free again for re-marking. If a slot is re-booked after a cancellation, the **active** appointment (pendente/confirmada) takes visual precedence in the cell; the historical one is reachable via the cell detail (planner decides stacking, but the active booking must be the dominant visual).
- Month view (D-18) stays indicator-only: it MAY add a small count of appointments per day alongside the free-slot count, but never renders appointment cells or times.

### 3. Pending-requests surface (D-05 / APPT-03)

- **Location:** a **"Pedidos a confirmar" panel** on the Agenda page, adjacent to the calendar (right side on ≥`lg`, stacked above/below on smaller viewports) — a `Card` with the heading + a count badge. Rationale: pending requests are cross-day and time-sensitive; a dedicated list is faster than hunting dashed cells across the grid (design skill: speed on frequent actions). The dashed pendente cells in the grid are the in-context echo; the panel is the actionable queue.
- **Each request row:** patient name (`text-base`) + responsável (`text-sm muted`) + slot **{data} {horário}** + `Pendente` badge, with two inline actions: **Confirmar** (`Button size="sm"`, accent) and **Recusar** (`Button size="sm" variant="outline"`, opens the destructive `AlertDialog`).
- **Confirmar** → pending → confirmed (cell flips to Confirmada treatment; toast "Pedido confirmado."). **Recusar** → pending → cancelada, releases the slot (toast "Pedido recusado."). Both update the grid and the panel count optimistically/after action result.
- **Empty:** the dashed-border empty state copy above.
- This phase, the doctor **creates** appointments as Confirmada directly (D-05); the pending queue exists and is actionable now (APPT-03), populated by the assistant in Phase 9.

### 4. Status transition affordances (APPT-02 / D-06)

- **From a confirmed appointment** in the grid: a `dropdown-menu` (or the detail popover) anchored to the cell, opened by clicking/focusing the booked cell, exposes the allowed transitions only:
  - Confirmada → **Marcar como realizada** (done) · **Marcar falta** (no_show) · **Cancelar consulta** (canceled, destructive `AlertDialog`).
- **Final states** (realizada/falta/cancelada) show a read-only detail (badge + patient + slot), **no transition items** (D-06 — no reopen this phase).
- Transitions are single, explicit menu items with the copy above; each returns a `sonner` toast. Destructive/slot-releasing transitions (cancelar) use the `AlertDialog`; realizada/falta use a direct menu item.
- The cycle is strictly `solicitada (pending) → confirmada → realizada | falta | cancelada`, and `recusar` (from pending) = cancelada (D-06). The UI never offers a transition outside this cycle.

### 5. States & consistency with Phase 6

- **Loading / saving / error / empty** follow the Phase 6 patterns verbatim (Skeleton for loading, `sonner` for outcomes, dashed-border empty states, inline `text-destructive text-sm` for field validation). The slim toolbar, Tabs, and discard-guard `AlertDialog` from `calendar-editor.tsx` are unchanged.
- All new copy is PT-BR. All new fills/borders/badges consume tokens only (no hex/rgb), per the design skill token table and Phase 6 contract.
