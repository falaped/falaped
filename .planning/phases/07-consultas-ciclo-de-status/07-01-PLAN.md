<objective>
Establish the database foundation for appointments: the `appointment_status` pg enum, the owner-scoped `appointments` table with RLS + 4 policies, the `btree_gist` extension, and the partial GiST exclusion constraint that guarantees non-double-booking (APPT-04 / D-08). Downstream plans (modules/actions/UI) depend on the live schema and must not run before the push is verified.

Purpose: Only the DB can arbitrate concurrent double-booking races (TOCTOU-safe); the exclusion constraint is the single authoritative invariant. The enum + transitions define the status cycle.
Output: Migration file, `appointment_status` enum + `appointments` table live in the DB, pure transition helper + spec, Zod schemas.
</objective>

  <action>
    Write a single migration `supabase/migrations/20260722200000_appointments.sql` combining (in this order):
    1. `create extension if not exists btree_gist with schema extensions;` — MUST come before the table (Pitfall 1: EXCLUDE with `=` on uuid fails without it).
    2. `create type public.appointment_status as enum ('pending','confirmed','done','no_show','canceled');` with a `comment on type` describing the cycle (values in English per UI-SPEC "DB value" column; PT-BR labels live in the UI badge — mirrors patient_sex).
    3. `create table public.appointments` with columns: `id uuid primary key default gen_random_uuid()`, `profile_id uuid not null references public.profiles(id) on delete cascade`, `patient_id uuid not null references public.patients(id) on delete restrict`, `status public.appointment_status not null default 'pending'`, `starts_at timestamptz not null`, `ends_at timestamptz not null`, `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()`.
    4. Named CHECK: `constraint appointments_ends_after_starts check (ends_at > starts_at)`.
    5. Named exclusion constraint `appointments_no_double_booking exclude using gist (profile_id with =, tstzrange(starts_at, ends_at, '[)') with &&) where (status in ('pending','confirmed'))`. The half-open `[)` is mandatory (matches Phase 6 slot semantics; Pitfall 2). The partial WHERE implements D-07 (only pending+confirmed hold the slot).
    6. Index: `create index idx_appointments_profile_starts on public.appointments (profile_id, starts_at);`.
    7. `alter table public.appointments enable row level security;` then 4 policies (select/insert/update/delete) `to authenticated`, each using the predicate `profile_id in (select id from public.profiles where auth_user_id = auth.uid())` — copy the exact policy shape from patient_vaccine_doses.sql (insert uses `with check`, update uses `using` + `with check`, select/delete use `using`).
    PINNED DEVIATION (research A3 / Pitfall 5): `patient_id` uses `on delete restrict` (NOT cascade like the patient_vaccine_doses mold) to preserve appointment history that Phase 10 (ganhos→consulta FK) will reference. `profile_id` keeps `on delete cascade`. Encode this explicitly per D-08.
    Do NOT create an RPC — a single `.insert()` is atomic (Pitfall 6); double-booking is guaranteed by the constraint, not a transaction.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Server Action | Untrusted appointment input (patient_id, starts_at, ends_at) crosses here; validated downstream (Plan 02) |
| Server Action → Postgres | profile_id stamped server-side; RLS + FK + exclusion enforce ownership and the double-booking invariant |
| authenticated user → RLS | RLS restricts rows to the owner's profile_id; the paid gate lives in the app layer (Plan 02), not RLS |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Elevation of Privilege | appointments table (cross-profile IDOR) | high | mitigate | RLS 4 owner-scoped policies with `profile_id in (select id from profiles where auth_user_id = auth.uid())`; FK + exclusion scoped by profile_id; ownership stamped server-side in Plan 02 (never from client) |
| T-07-02 | Tampering | double-booking / concurrent race (TOCTOU) | high | mitigate | Partial GiST exclusion constraint in the DB — the invariant lives in the DB, not app code; the only correct arbiter of concurrent races (23P01 on violation) |
| T-07-03 | Information Disclosure | patient history loss via FK cascade | medium | mitigate | patient_id ON DELETE RESTRICT preserves appointment history (a patient with appointments cannot be deleted), protecting the Phase 10 earnings FK |
| T-07-SC | Tampering | npm/pip/cargo installs | high | accept | No new packages this phase (RESEARCH Package Legitimacy Audit: none new); only the Postgres contrib extension btree_gist (bundled with Supabase, not a third-party package) |
